---

## 1. 为什么要用「楼层级节点」

X6 号暖廊的官方原文是：

```
X6暖廊（A10公寓东2层—A10公寓西3层）
```

两端**都在 A10公寓**。如果暖廊端点还是"建筑 ID"，这条数据根本存不进去——
起点建筑 = 终点建筑，会被当成自环。

所以端点的粒度必须细到「建筑 + 楼层 + 方位」：

| | 旧模型 | 新模型 |
|---|---|---|
| 端点 | `from_building_id` | `from_node_id` |
| 能否表达 X6 | ❌ 同一栋楼 | ✅ 东侧2层 ≠ 西侧3层 |
| 自环规则 | 建筑不能等于自身 | **节点**不能等于自身 |
| 同一栋楼多段暖廊 | 无法区分 | 用不同节点区分 |

`节点 = 建筑（building_id） + 楼层（floor） + 方位（zone，如"东/西"）`

## 4. 一条暖廊什么时候能进 `corridors.js`

必须同时满足三条，缺一条就进 `candidates.js`：

1. **两端都是明确的建筑楼层节点**（不能是"某条暖廊"）；
2. **官方原文完整可读**（被遮挡/截断的不算）；
3. **没有未决的分支或暖廊接口**（例如原文末尾带「，N4暖廊」）。

按这个标准，N2 / N3 / N5 都被留在了候选：

| 编号 | 卡在哪 |
|---|---|
| N2 | 「A16公寓3层—A15公寓、A13公寓、A01公寓3层」用顿号分隔，无法判断是串联还是并列 |
| N3 | 末尾「，N4暖廊」表示还与另一条暖廊相接，分支位置未定 |
| N5 | 一端接的是「N4暖廊」而不是建筑 |

## 6. 校验与测试

```powershell
npm run check:data
```

覆盖四类校验，既有正向（真实数据必须过），也有负向（故意造脏数据必须被拦住）：

### 6.1 节点引用

- 暖廊引用了不存在的节点 → 拦
- 串联节点里出现不存在的节点 → 拦
- 串联节点首尾与起点/终点不一致 → 拦
- 4-3 的串联顺序必须与官方原文一致（明德楼 → 格物楼 → 建筑设计学院）

### 6.2 编号重复

- 暖廊项目编号重复 → 拦
- 官方编号重复 → 拦
- 节点编号重复 → 拦
- 建筑名称重复 → 拦

### 6.3 楼层

- 非法写法（如「二楼」）→ 拦；只接受 `1层` / `2.5层` / `M层` 这类官方写法
- 暖廊的 `floors` 描述与两端节点的楼层对不上 → 拦
- 两端楼层已知但 `floors` 为空 → 只警告，不拦

### 6.4 同建筑连接

- 同一栋建筑的不同节点相连 → **允许**（X6 就是这种情况）
- 起点节点 = 终点节点（自环）→ 拦
- 同一栋楼同一层同一方位出现两个节点 → 拦（无法区分）

当前结果：**19 项全部通过**。

## 7. 新增一条记录的步骤

1. 先在 `nodes.js` 建节点（端点必须是节点，不是建筑）：

```js
createNode({
  node_id: 'YQ1-N-012',
  building_id: 'YQ1-B009',   // 必须已在 buildings.js 里
  floor: '3层',               // 官方未标注就写 null
  zone: null,
  display_name: '正心楼 3层',
  source: '[official_map] 官方地图暖廊弹窗截图 ｜ 日期 ｜ 采集人'
})
```

2. 再在 `corridors.js` 建暖廊：

```js
createCorridor({
  corridor_id: 'YQ1-WC-0007',
  official_no: 'X3',
  official_description: '<官方原文，逐字>',
  from_node_id: 'YQ1-N-012',
  to_node_id: 'YQ1-N-005',
  floors: '3层 ⇄ 2.5层',
  source: '[official_map_popup] 官方地图暖廊弹窗截图 ｜ 日期 ｜ 采集人'
})
// length_m / access_status / bidirectional 会自动套用项目规则
```

3. 跑 `npm run check:data`，全绿才算录入成功。

**多栋串联**：在 `chain_node_ids` 里按原文顺序写全部节点，起止仍取两端的节点；
不要拆成多条暖廊，也不要在中途节点上假设出入口。

## 7. 楼间暖廊路线查询（BFS）

真实模式里，学生只需要选「起点建筑 / 终点建筑」，不用管楼层。

算法在 `src/utils/realRoutePlanner.js`，和模拟校园的 Dijkstra 是**两套独立实现**：

| | 模拟校园 | 真实校园 |
|---|---|---|
| 算法 | 加权 Dijkstra | **0-1 BFS** |
| 比较什么 | 加权后的"体感成本" | **官方暖廊段数** |
| 有距离吗 | 有 | **没有（全是 null）** |
| 能算步行时间吗 | 能 | **不能** |

### 7.1 建图规则

| 边 | 连接 | 代价 | 性质 |
|---|---|---|---|
| 官方暖廊边 | 暖廊的 `from_node` ⇄ `to_node` | **1** | 官方确认 |
| 楼内换乘边 | 同一栋建筑里已录入的节点两两相连 | **0** | **课程建模假设** |

> 楼内换乘边**只作用于同一栋建筑内部**，不会生成任何跨楼连接。
> 跨楼的每一段都必须出现在 `corridors.js` 里，否则路线就是"未连通"。

起点建筑的所有节点都是起点集，终点建筑的所有节点都是终点集，
所以在建筑内换乘、选哪个门进，都由算法自己决定。

### 7.2 这条假设的三个后果（写报告可以用）

1. **楼内换乘不增加段数**：A03公寓 → 学士楼 共 3 步，但只算 **2 段**官方暖廊。
2. **X6 在楼间路由里不再是必经之路**：A10公寓东侧2层 → 西侧3层 本来要过 X6，
   但既然同楼换乘免费，算法直接换乘即可；X6 仍然保留在数据和详情里。
3. **节点级仍然不连通**：诚意楼 2层 与 2.5层 之间没有边，
   是"建筑级"的路由假设把它们连起来的 —— 这是假设，不是事实。

### 7.3 自检

```powershell
npm run check:real-route
```

27 项，覆盖：

- 图结构（6 条暖廊 = 12 条有向边、串联只算一条边）
- 节点级：直连 / 多段 / 同建筑节点 / 未连通 / 同点 / 未知节点
- **建筑级**：直连、多段 + 楼内换乘、串联算一段、同建筑、跨组团不连通、
  不凭空生成跨楼连接、结果不含距离字段

## 8. 与模拟数据的关系

`src/data/buildings.js` 与 `src/data/corridors.js`（模拟数据）**完全没动**，网页仍用它们。
本目录尚未接入 `routePlanner.js`，`dataset.js` 也还没有被页面引用，所以：

- 现有地图、路线规划、三种偏好全部照常工作；
- 接入时只需把数据源从模拟换成 `dataset.js` 的 `REAL_CAMPUS`，算法不用改；
- 接入后界面必须显示免责声明
  「本系统为课程演示作品，暖廊通行状态基于建模假设，实际以学校公告为准。」
  （常量见 `rules.js` 的 `DISCLAIMER`，已在页面顶部展示）。

## 9. 示意地图布局（人工标定）

`mapLayout.js` 把 19 栋建筑按官方截图的**相对方位**排到 1200×800 画布上。

| 状态 | 数量 | 地图表现 |
|---|---|---|
| `calibrated` 已标定 | 7 | 正常绘制实线框 |
| `estimated` 位置待核实 | 1（建筑设计学院） | 虚线框 + "位置待核实" |
| `unplaced` 未标定 | 1（A10公寓） | **不上图**，只在右下角清单里列出 |

**三条硬规则**（由 `validateLayout()` 强制）：

1. `unplaced` 不许带 `footprint` —— 带了就等于伪造位置；
2. 所有足迹必须落在校园示意边界内；
3. 建筑表里每一栋都必须有布局记录（哪怕只是 `unplaced`）。

**暖廊怎么画**：没有真实走向数据，所以全部用**示意虚线**；
端点未标定的暖廊直接不画（当前 6 条里画 4 条，X2 / X6 因 A10公寓未标定而跳过），
页脚会写明"另有 N 条因端点未标定未绘制"。

**视图操作**：滚轮缩放、拖动画布、"适应"按钮自动把内容撑满画布。
这些操作只移动"相机"，**不改变任何建筑的相对位置**，也不改动标定数据。

**精度**：方位正确、比例近似，误差约 ±40–60 画布单位。
这是人工标定，**不是测绘数据**，界面上常驻"人工标定 · 课程演示 · 非测绘精度"。
